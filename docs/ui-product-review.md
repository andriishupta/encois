# Dashboard product review

This document records the product-level dashboard review against the current control plane, Gateway contracts, workflow runtime, source ingestion model, and authorization boundaries.

## Canonical product model

```text
Template catalog ──create intent──> Preview / Change Plan ──approve + apply──> Blueprint registry
                                                                                       │
                                                                                       └──start──> Workflow Run ──> Events / Evidence

Organization Integration ──provider capability──> Unit Source ──> Revision ──> Ingestion ──> Graph / Agent Memory
```

The dashboard must not ask a user to provide runtime IDs that the Gateway can resolve from a selected Template, approved Blueprint, provider capability, organization scope, and business input. IDs remain technical details for diagnostics, audit, and support.

## Definition of done for the dashboard slice

- The user chooses a product concept, not a Runtime implementation detail.
- The API validates organization scope and permission before loading or applying state.
- Preview is read-only; submit creates a plan; approve records a human decision; apply mutates the Blueprint registry or starts a Run.
- A Run is inspectable through status, events, evidence, freshness, and audit metadata.
- Missing backend capabilities are represented as explicit unavailable states, never as disabled fake forms or invented data.
- A failed read never renders a false zero or a false “queue clear” state; affected metrics and queues show unavailable state with a retry action.
- Template provider slots are resolved server-side against active, scope-visible integrations and their granted capabilities; the browser receives status and display metadata, never integration IDs. Source creation follows the same server-side credential and binding checks. Provider authorization enters through a service-only credential-reference boundary.
- Run control, Source freshness, saved investigations, in-product notifications, OAuth state, provider credential references, provider health callbacks, versioned workflow-plan metadata, Run retention deadlines, scheduled health dispatch, tenant-scoped retention cleanup, server-side refresh rotation, terminal Blueprint runtime trace projection, and API-backed onboarding state are persisted or deployment-wired and contract-tested; distributed live streaming, provider budget emission, visibility-array indexing, and multi-hop graph traversal remain explicit follow-up work.
- Graph inspection remains read-only, while Memory mutations are approval-gated and audited; both surfaces use scoped Gateway queries and separate permission boundaries. Graph blocker relationships now remain visible in the projection and common filters push down to Spanner; visibility-array indexing and multi-hop traversal remain scale follow-ups. Runtime evidence projection now preserves terminal step provenance, freshness, and optional confidence; retention metadata and richer live provider/run linkage remain before calling the admin experience complete.
- The authenticated shell and dashboard surfaces must remain usable at desktop and mobile breakpoints: primary, catalog, lifecycle, source-detail, governance, and settings routes must not create document-level horizontal overflow. The current responsive audit covers the available route set at 390px and 1280px viewports with zero overflow and no browser warnings.
- Dashboard Next actions must be generated from permission-aware server projections, persisted per organization/user scope, and expose an audited Accept/Dismiss lifecycle; unavailable backend data must remain unavailable until the server projection exists.
- Workflow plans must persist the planner name/version, source-schema version, prompt version/hash, and a stable combined fingerprint so administrators can inspect historical planning inputs without exposing raw prompts.
- Workspace onboarding settings must expose lifecycle state, coordination mode, and catalog choices without accepting Coordinator or Temporal runtime IDs from the browser; changes must remain permission-gated, persisted, and explicit about the separate start action.

## Production release gates

The dashboard/control-plane slice is production-shaped and locally verified, but a hosted production release still requires these external gates:

- Configure the deployed OAuth provider catalog, callback URL, Secret Manager project, private Agent Gateway service-account access, and provider refresh entries. The generic authorization path, hosted GitHub/Jira read adapters, tenant-scoped active-provider health scheduling, and server-side refresh/rotation path are implemented; each provider still needs its real OAuth endpoint/client policy and a hosted smoke test.
- Configure `ENCOIS_PUBLIC_BASE_URL` to the externally reachable Gateway origin, deploy the API service account's least-privilege Secret Manager role, and provision each provider webhook through the Integration detail page. Verify the one-time secret handoff, provider signature, endpoint disable/enable behavior, and rotation in the target environment.
- Run the protected Cloud Run migration Job for migrations 0000–0020 in the target Cloud SQL environment using the separate `cloud-sql-migration-url` secret and DDL-capable operator role. Build the runtime `@encois/persistence` package together with the API; a TypeScript-only check is insufficient because the API imports the package runtime entry point.
- Configure Identity Platform, Temporal Cloud, Agent Gateway GCP mode, Spanner schema/IAM, Agent Platform Memory Bank, Cloud Storage, and redacted OpenTelemetry export for the target environment.
- Keep the API readiness endpoint wired to real dependency probes in the hosted environment; local verification now fails Agent Gateway/Runtime readiness when their `/health/ready` endpoints cannot be reached, but Temporal connectivity, Identity Platform, Cloud SQL, and provider authorization still need hosted smoke tests.
- Apply migrations through `0020_add-organization-onboarding`, configure the protected retention DB URL and explicit organization schedule targets, and verify the cleanup execution before relying on long-term investigation and access-governance audit as a compliance record. Temporal history, large artifacts, webhook payloads, and provider-specific erasure still require their own retention policy.
- Hosted-smoke-test webhook ingress with real provider signatures, Secret Manager resolution, Cloud Storage access, retry/replay behavior, and Temporal handoff. The local route and contract are implemented, but external provider delivery semantics and production retention/dead-letter operations are not verified from this workspace.
- Add delivery adapters only when email/push/digest are part of the product contract; in-product notifications are the current bounded behavior.
